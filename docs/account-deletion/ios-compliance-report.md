# iOS account deletion source review — 2026-10-19

Source flow: **Your Account → Privacy & Data → Delete Account**, implemented by `app/sign-in.tsx`, `AccountPanel.tsx` and `DeleteAccountPanel.tsx`. Initiation requires no support conversation and is independent of entitlement. The panel explains immediate access restriction, the server-recorded 30-day recovery period, subsequent permanent processing, shared ownership exceptions, store-managed cancellation, 365-day minimal proof, seven-day completion outbox and privacy/support routes. The gate distinguishes pending, review, unavailable, restored and independently verified purge. Local tests verify unavailable/expired proof refusal, explicit local reset and actor switching.

[Apple guideline 5.1.1(v)](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion/) permits recent authentication and reasonably timed processing when honestly disclosed; it requires in-app initiation, associated-data removal and completion information. No numerical conflict with the approved 30-day recovery period was found in that guidance. This is not an opinion that the grace period satisfies every applicable privacy law; Legal must approve the disclosure and jurisdictional timing before submission.

Sign in with Apple uses a random nonce, sends its digest to Apple and raw nonce to Supabase, and captures the authorization code only for a server exchange. The server verifies Apple's signed identity-token issuer/audience/subject against the authenticated user's Apple identity, encrypts the refresh token with AES-GCM, and stores it service-side. Revocation uses Apple's `/auth/revoke` endpoint and the approved `APPLE_DELETION_CLIENT_ID`, `APPLE_DELETION_TEAM_ID`, `APPLE_DELETION_KEY_ID`, `APPLE_DELETION_PRIVATE_KEY` names. Provider failures and missing legacy material remain incomplete; they never produce successful provider evidence. The worker records provider names from the verified Auth identity and cannot infer a missing Apple identity from an unavailable lookup.

Token-revocation design follows [TN3194](https://developer.apple.com/documentation/technotes/tn3194-handling-account-deletions-and-revoking-tokens-for-sign-in-with-apple). Source-side nonce/subject/failure checks are covered; actual Apple Developer capabilities, server notification configuration and live revocation are **NOT_VERIFIED**. The owner explicitly deferred live Apple/Google revocation; that restriction was preserved. No different person's Apple identity was touched.

The project declares `ios.usesAppleSignIn=true`, bundle `com.herkeys.app`, and the Expo Apple Authentication plugin. This declaration is not proof of actual signed entitlements. Windows provides no iOS Simulator/Xcode; all native journeys are NOT_RUN. Apple subscription management points to `https://apps.apple.com/account/subscriptions`; deletion does not cancel or refund a store subscription.

`APPLE_SOURCE_COMPLIANCE=PASS` means the reviewed source supports the required flow and fail-closed semantics. **APPLE_COMPLIANT is not claimed.** Submission still requires published legal disclosures, a functioning public recovery route, actual native/entitlement evidence and owner-authorized live revocation or an explicitly accepted remaining gate. Reviewer demonstration must include discovery, recent verification, pending/recovery, shared review and terminal proof; no release build was produced for this sprint.
